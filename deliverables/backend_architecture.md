# Backend architecture — Yamicc demo v3

Status: W1 contract, 2026-11-21. Everything is synthetic and local. No hosting, no real patient data, no paid APIs.
Contract: `backend/openapi.json` (generated by FastAPI, committed; a test fails if it is stale). JSON is **camelCase**.

## 1. C4 container view

```
 Nurse / Monitor / PI
        │ (browser-free: desktop app)
        ▼
┌──────────────────┐  HTTPS-less localhost REST + SSE   ┌────────────────────────┐
│ Flutter app      │ ─────────────────────────────────▶ │ Backend API (FastAPI)  │
│ (Zeta UI)        │      Bearer JWT (nurse|monitor|pi)  │ :8000  backend/app     │
└──────────────────┘                                     │ auth · review · audit  │
                                                         └───────┬───────▲────────┘
                                          SQL (psycopg)          │       │ REST, Bearer JWT (role "service")
                                                         ┌───────▼───┐ ┌─┴──────────────────┐
                                                         │ Postgres  │ │ AI service (W4)    │
                                                         │ :5433     │ │ backend/app/ai     │
                                                         └───────────┘ │ provider interface │
                                                                       └─┬──────────────────┘
                                                                         │ local only
                                                                  Ollama / fixture replay
```

- **Flutter app** talks only to the API. No direct DB, no direct AI calls.
- **Backend API** owns all state and all rules: auth, role checks, review decisions, eCRF values, audit chain.
- **Postgres** is the system of record. Schema: `backend/migrations/*.sql` (applied by `app.db.migrate`).
- **AI service** is a separate process. It never writes to the DB. It polls `GET /runs?status=queued`, reads documents through the API, and posts proposals through the API. This keeps the audit trail and the span checks in one place.

## 2. Data model (Postgres)

| Table | Key columns |
|---|---|
| `study`, `site` | study meta (milestones/alerts/tasks in `study.meta` jsonb); 3 sites |
| `app_user` | username, role `nurse\|monitor\|pi\|service`, pbkdf2 hash |
| `participant` | pseudonymised id `GBM-NL-00x`, site, status, treatments |
| `visit` | participant, name, date, status |
| `ecrf_field` | field id (`MGMTPROM` …), label, section, value type, terminology, CDISC info — from `study.json` |
| `source_document` | id, participant, type, language, full text, sha256 |
| `extraction_run` | participant, optional document, status `queued\|running\|completed\|failed`, `done/total`, provider, model, prompt version |
| `extraction` | run, document, field, status `proposed\|abstained`, value, normalized value, confidence, proposed code, **span start/end + evidence**, provider, model, prompt version, `review_state` |
| `review_decision` | extraction, decision `accept\|correct\|reject\|defer`, corrected value, reason, user, role (history; latest wins) |
| `ecrf_value` | (participant, field) → verified value, code, source extraction, verified by/at, SDV by/at |
| `data_query` | participant, site, field, status `open\|closed`, text |
| `audit_event` | seq, ts, actor, role, action, entity, participant, before, after, source `human\|ai`, model, prompt version, `prev_hash`, `hash` |

### Review rules
- `accept` copies the AI value (and its code) to `ecrf_value`. `correct` needs `correctedValue`; the code is dropped because it no longer matches. `reject` needs `reason`. `defer` changes only the state. Accepting an abstained extraction is refused (422).
- A later decision on the same extraction replaces the earlier one. If the earlier decision created the eCRF value and the new one is reject or defer, the value is removed.
- Each decision writes `extraction.decision` (source `human`, with the model and prompt version of the proposal) and, when the eCRF value changes, `ecrf.value_set` or `ecrf.value_cleared`. All in one DB transaction.
- SDV (`POST /participants/{id}/ecrf/{field}/sdv`) is monitor-only. A new verified value resets SDV.

### Roles
| Role | May |
|---|---|
| nurse | read, review, create runs, close queries |
| pi | same as nurse, plus open queries |
| monitor | read, SDV, open and close queries. **Cannot review.** |
| service | AI service only: update runs, post extractions |

### Dashboard KPIs (all SQL, `GET /studies/{id}/dashboard`)
Enrolled vs target; eCRF completeness = verified values ÷ (participants that have source documents × fields); extraction counts per review state; AI acceptance rate = accepted ÷ (accepted + corrected + rejected); needs attention = pending and (abstained or confidence < 0.6); open queries; SDV done/pending; audit event count.

### Audit chain
`hash = SHA-256(prev_hash + canonical_json(ts, actor, role, action, entity_type, entity_id, participant_id, before, after, source, model, prompt_version))`. Canonical JSON: sorted keys, no spaces. The first `prev_hash` is 64 zeros. Appends take `pg_advisory_xact_lock`, so the chain cannot fork. A trigger rejects UPDATE, DELETE and TRUNCATE. `GET /audit/verify` walks the chain and returns `{ok, count, brokenSeq, reason, headHash}`. A removed last event is only visible if you keep an earlier `headHash`.

## 3. Trust boundaries

1. **App ↔ API:** the only user-facing boundary. JWT (HS256, 8 h). Roles are enforced server-side, never in the app.
2. **AI service ↔ API:** the AI service is untrusted for correctness. It has role `service`. The API checks that each evidence span equals the stored document text (422 otherwise), that the field exists, and that the document belongs to the run's participant. AI output is only ever a *proposal*; a human decision is needed before an eCRF value exists.
3. **API ↔ DB:** only the API holds DB credentials. The audit table is append-only by trigger.
4. **Local-only:** CORS is open and the JWT secret has a default. This is acceptable for a localhost demo and must change before anything is hosted. No data leaves the machine.
5. **Data:** synthetic only; every API response about data carries the disclaimer through `/studies/{id}/dashboard` and the app must show it on screen.

## 4. AI provider interface (for `backend/app/ai`, W4)

Flow of an extraction run:
1. App: `POST /participants/{id}/extraction-runs` `{documentId?}` → run `queued`.
2. AI service: `GET /runs?status=queued`, `GET /documents/{id}` for the text, `GET /participants/{id}/ecrf` for the field list.
3. AI service: `PATCH /runs/{id}` `{status:"running", total, provider, model, promptVersion}`.
4. AI service: `POST /runs/{id}/extractions` with a list of proposals (batch per document is fine). Each carries `documentId, field, status, value, normalizedValue, unit, confidence, proposedCode, abstentionReason, evidence[{start,end,text}], provider, model, promptVersion`. `done` rises by the batch size.
5. AI service: `PATCH /runs/{id}` `{status:"completed"}` (or `failed` + `error`).
6. App: `GET /runs/{id}/events` (SSE, event `progress`, data = Run JSON) or poll `GET /runs/{id}`. EventSource clients pass `?access_token=`.

Suggested Python interface (the provider is swappable; the fixture provider replays `app/assets/data/extractions.json`):

```python
class Proposal(TypedDict):          # = ExtractionIn in openapi.json
    documentId: str; field: str; status: Literal["proposed", "abstained"]
    value: str | None; confidence: float; evidence: list[dict]  # start, end, text
    # + normalizedValue, unit, proposedCode, abstentionReason

class ExtractionProvider(Protocol):
    name: str                       # "ollama", "fixture"
    model: str
    prompt_version: str
    def extract(self, document_text: str, document_type: str, fields: list[dict]) -> list[Proposal]: ...
```

Seeded data: the 46 fixture extractions load as 10 completed runs with provider `fixture`; each has an `extraction.proposed` audit event (source `ai`).

## 5. Known limits (W1)
- No refresh tokens, no password change, no pagination except `/audit`.
- Queries have two states (open, closed); no reply thread.
- Embedded fallback Postgres (`app.devpg`) is for machines without Docker.
